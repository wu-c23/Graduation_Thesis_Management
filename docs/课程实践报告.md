## 摘要

毕业设计过程涉及选题、需求、原型、设计、开发、测试与答辩等多个环节，传统管理方式依赖线下表格和即时通讯工具，存在进度不透明、材料版本混乱、导师难以及时掌握整体情况等问题。本项目设计并实现了一个面向学生与导师的毕业设计过程管理平台，将过程固化为“需求文档 → 原型 → 设计评审 → 周报 → 代码仓库 → 测试报告”六个步骤。

系统采用 Vue 3 + Spring Boot 3 的前后端分离架构，使用 JWT 实现登录与角色隔离，使用 MyBatis-Plus 访问 H2/MySQL 数据库。系统不单独维护“阶段完成表”，而是根据材料、评审、周报、仓库等真实业务数据实时计算六步进度，并以“连续完成前缀”避免状态回退带来的统计失真。导师端提供批量总览，将学生进度矩阵、完成率、待办与最近动态集中在一屏展示。

系统经过 36 个自动化测试、42 项端到端接口检查和 8 条手工验收场景验证，可在本地完整演示六步流程。由于课程环境暂无服务器，本次未执行线上部署，交付范围为源码、本地运行方式与全套文档。

**关键词**：毕业设计管理；前后端分离；过程管理；权限控制；Spring Boot；Vue

## 1. 项目背景与目标

### 1.1 背景

毕业设计周期通常持续数月，学生需要提交多类材料，导师需要同时指导多名学生。若使用线下表格或聊天工具收集材料，常见问题包括：

- 导师无法快速判断每名学生处于哪一步、是否需要处理；
- 材料多次修改后版本混淆，退回原因难以追溯；
- 周报、代码仓库、测试报告分散在不同平台，进度缺少统一口径；
- 学生不清楚下一步该做什么，导师也难以按统一规则验收。

### 1.2 项目目标

本项目不追求覆盖毕业设计全流程的所有细节，而是聚焦“过程可追踪、材料可审核、进度可汇总”三个核心目标：

1. 将过程固定为六个可审核的步骤；
2. 学生按步骤提交材料，导师按统一步骤审核；
3. 六步进度由真实数据计算，学生端、导师端展示一致；
4. 导师能在一屏内看到名下所有学生的进度、完成率与待办；
5. 在课程规模下保持实现简单、可运行、可演示。

### 1.3 范围边界

明确不做：选题双选、答辩排期、论文查重、即时聊天、消息推送、复杂统计报表、多级学院管理。范围在第 1 周冻结，后续只修复缺陷和补充展示，不新增业务功能。

## 2. 需求分析

### 2.1 角色

| 角色 | 职责 |
|---|---|
| 学生 | 查看本人课题、提交材料与周报、绑定代码仓库、提交测试报告、查看审核结果 |
| 导师 | 查看名下学生总览与详情、审核材料、设计评审、批阅或退回周报、查看仓库信息 |

### 2.2 六步流程

| 步骤 | 学生操作 | 导师操作 | 完成条件 |
|---|---|---|---|
| 1 需求文档 | 上传文件或填写外链 | 通过 / 退回 + 评语 | 最新需求材料为“已通过” |
| 2 原型 | 上传文件或填写外链 | 通过 / 退回 + 评语 | 最新原型材料为“已通过” |
| 3 设计评审 | 查看评审结果 | 打分、结论、评语 | 需求与原型均通过，且最新评审为 PASS |
| 4 周报 | 按周提交进展 | 批阅或退回 | 至少 1 篇周报为“已批阅” |
| 5 代码仓库 | 绑定公开仓库、同步或手工填写 | 只读查看 | 已绑定且最近同步成功 |
| 6 测试报告 | 提交报告与统计 | 通过 / 退回 + 评语 | 最新测试报告为“已通过” |

### 2.3 功能需求

**学生端**

- 登录、退出、Token 失效处理；
- 查看本人课题与六步进度；
- 提交需求、原型、测试报告（文件或外链二选一）；
- 查看材料历史、导师评语、评分并下载附件；
- 查看设计评审历史；
- 提交、修改重交周报；
- 绑定 GitHub / Gitee 公开仓库，自动同步提交统计；
- 同步失败时手工填写提交数和最近提交时间。

**导师端**

- 查看名下学生总览：人数、待办、平均完成率、最近动态；
- 查看每名学生六步状态矩阵；
- 搜索、筛选、排序；
- 查看学生详情并审核材料；
- 进行设计评审；
- 批阅或退回周报；
- 查看代码仓库同步信息。

### 2.4 非功能需求

| 类别 | 要求 |
|---|---|
| 安全 | 密码 BCrypt 存储；JWT 鉴权；角色与数据归属双重校验；上传白名单与大小限制 |
| 一致性 | 学生端、导师详情、导师总览共用同一进度计算逻辑 |
| 可用性 | 同步失败、网络异常有明确提示与兜底入口 |
| 可运行性 | 本地一条命令启动后端、一条命令启动前端，无需外部数据库 |
| 可维护性 | 分层清晰，状态枚举固定，异常统一处理 |

## 3. 系统设计

### 3.1 总体架构

```text
浏览器（Vue 3 + Element Plus）
        │  HTTP / JSON + JWT
        ▼
Vite 开发代理 / Nginx（后续部署）
        │
        ▼
Spring Boot 3（Controller → Service → Mapper）
        │
        ├── H2 文件库（开发/课程演示）
        ├── MySQL 8.0（脚本预留）
        ├── uploads/（材料附件）
        └── GitHub / Gitee 公开 API（仓库统计）
```

前后端分离，前端只负责展示与交互，所有权限判断和业务规则在后端执行。前端不能通过传入 `studentId` 或 `advisorId` 改变数据归属，身份统一从 JWT 读取。

### 3.2 数据模型

系统共 6 张表：

| 表 | 作用 | 关键字段 |
|---|---|---|
| `sys_user` | 用户 | `username`、`password`、`role`、`real_name` |
| `project` | 课题 | `title`、`student_id`、`advisor_id` |
| `artifact` | 材料 | `project_id`、`type`、`status`、`file_path`、`external_url`、测试统计 |
| `design_review` | 设计评审 | `project_id`、`round_no`、`score`、`result`、`comment` |
| `weekly_report` | 周报 | `project_id`、`week_no`、`content`、`status`、`comment` |
| `repo_binding` | 仓库绑定 | `project_id`、`repo_url`、`repo_host`、`commit_count`、`sync_status` |

设计要点：

- 材料采用“追加版本”而不是覆盖更新，保留每次提交历史；
- 周报按 `(project_id, week_no)` 唯一保存，同一周只保留一条，退回后原地重交；
- 设计评审按轮次保留历史；
- 不建“阶段完成表”，避免业务数据与进度表不一致。

### 3.3 进度计算

六步状态由 `ProjectProgressService` 统一计算：

- 需求、原型、测试报告：取最新一条材料的状态，映射为已完成 / 审核中 / 已退回 / 未开始；
- 设计评审：要求最新需求与原型均通过，再检查最新评审结论；
- 周报：至少 1 篇最新周报为“已批阅”；
- 仓库：已绑定且最近同步状态为成功；
- 总完成数按“连续完成前缀”计算：中间任一步未完成，后续步骤即使有数据也不计入完成数。

这一设计解决了两个常见问题：

1. 状态口径分裂：总览、详情、学生端都调用同一服务，不会出现不同页面数字不一致；
2. 状态回退：材料重新提交后，后续步骤自动暂停计入，避免“已通过材料被替换但进度仍显示完成”。

### 3.4 接口设计

系统共 18 个接口，按角色划分：

| 分组 | 接口数 | 说明 |
|---|---:|---|
| 认证 | 2 | 登录、当前用户 |
| 健康检查 | 1 | 后端与数据库状态 |
| 学生端 | 8 | 课题、材料、周报、仓库绑定与同步 |
| 导师端 | 6 | 学生总览/详情、材料审核、设计评审、周报批阅 |
| 文件下载 | 1 | 鉴权附件下载 |

统一响应格式 `{ code, message, data }`；异常由全局处理器转换为明确的 HTTP 状态码与提示。

### 3.5 权限设计

- `AuthInterceptor` 校验 JWT，并把当前用户写入请求上下文；
- `/api/student/**` 仅允许 `STUDENT`，`/api/advisor/**` 仅允许 `ADVISOR`；
- Service 层再次校验课题归属：学生只能操作自己的课题，导师只能操作名下课题；
- 文件下载同样校验角色与课题归属，并校验规范化路径位于上传根目录内；
- 仓库 API 地址由固定主机与白名单字符构造，降低 SSRF 风险。

## 4. 系统实现

### 4.1 后端实现

后端基于 Spring Boot 3.3.5 与 Java 21，按 Controller / Service / Mapper 分层，主代码约 3000 行、50 个 Java 文件。

**登录与鉴权**：登录时用 BCrypt 校验密码，成功后签发 HS256 JWT，有效期 8 小时。拦截器解析 Token 并注入当前用户，未登录返回 401，角色不匹配返回 403。

**材料提交**：支持 multipart 文件与外部链接二选一；文件扩展名白名单、20MB 上限、文件名清洗、UUID 存储；外链仅允许 `http/https`；待审核期间禁止重复提交；每次提交新增记录。

**设计评审**：前置校验最新需求与原型均通过；评分 0–100；结论仅允许 PASS / RETURN；轮次递增。

**周报**：按课题与周次唯一保存；待批阅或已批阅不可重复提交；退回后原地重交并清空上一轮意见。

**仓库同步**：校验 GitHub / Gitee 地址并规范化；调用公开 API 获取提交总数与最近时间；连接超时 3 秒、请求超时 5 秒；异常落为 `FAILED` 而不是 500；提供手工填写兜底。

**导师总览**：按 `project_id IN (...)` 批量查询材料、周报、评审、仓库，计算待办、完成人数、平均完成率与最近动态，避免 N+1。

### 4.2 前端实现

前端基于 Vue 3、Vite、Element Plus 与 Axios，页面代码约 2300 行。

- 登录页：表单校验、健康状态展示、Token 存储；
- 学生工作台：六步进度条 + 五个 Tab（材料、设计评审、周报、仓库、测试报告）；
- 导师总览：四张统计卡片、学生表格、六步圆点矩阵、搜索筛选排序、详情抽屉；
- 请求封装：统一携带 JWT，401 自动清理会话并跳转登录；
- 文件下载：携带 JWT 请求 Blob 后触发浏览器保存，不在 URL 中暴露 Token；
- 状态展示：统一的枚举到中文标签、颜色映射。

### 4.3 关键实现难点

**难点一：进度口径统一。**
最初前端尝试自行汇总进度，导致总览与详情可能不一致。最终把计算全部收敛到后端进度服务，前端只展示。

**难点二：总览性能。**
逐学生查询会产生 N+1。改为按导师名下全部课题批量查询四类业务数据，再在内存中分组；课程规模下简单可靠。

**难点三：仓库同步的不确定性。**
公开 API 可能限流、超时或变更分页格式。系统设定短超时、失败状态和手工填写入口，保证演示不中断。

**难点四：状态回退。**
材料重新提交会让当前步骤回到审核中。通过“连续完成前缀”计算总完成数，并在页面提示用户原因。

## 6. 项目特色

### 6.1 进度由业务数据实时推导

系统不维护独立的进度表，而是从材料、评审、周报、仓库的真实状态计算六步进度。好处是：

- 不会出现“进度表说完成、材料却未通过”的矛盾；
- 退回、重交、重新同步后进度自动更新；
- 总览、详情、学生端共用一套口径。

### 6.2 导师总览服务于决策

总览不仅展示进度，还把待办、完成率、最近动态放在同一屏，并提供搜索、筛选、排序。导师可以快速判断“先处理谁”，而不是逐个点开学生详情。

### 6.3 对外部依赖提供降级路径

代码仓库同步依赖公开 API，存在限流与网络风险。系统在同步失败时保留明确状态，并提供手工填写入口，使演示不因外部服务不可用而中断。

## 7. 不足与改进方向

| 不足 | 影响 | 改进方向 |
|---|---|---|
| 仅支持单导师、单课题的课程规模 | 无法直接用于真实院系 | 增加学院/专业/导师组多级模型 |
| 仓库同步仅支持公开仓库 | 私有仓库需手工填写 | 接入 OAuth 或平台 Token |
| 文件保存在本地磁盘 | 多实例部署困难 | 接入对象存储与清理策略 |
| 未实现消息通知 | 学生需主动查看 | 增加站内提醒或邮件 |
| 前端包体积较大 | 首次加载略慢 | 按需引入组件、拆分路由 |
| 未做线上部署 | 无法远程访问 | 按运行说明完成服务器部署与回归 |
| 未做性能压测 | 规模扩大后未知 | 增加分页、索引与压测 |

## 8. 总结

本项目在 6 周、33 学时的课程约束下，完成了一个可运行、可演示、可验收的毕业设计过程管理平台。项目覆盖需求分析、原型、概要设计、编码、测试与文档的完整软件工程过程。

主要收获：

1. **先冻结范围，再谈扩展。** 课程时间有限，明确不做什么比不断增加功能更重要。
2. **把一致性放在展示效果之前。** 六步进度由统一服务计算，避免了多处逻辑分裂。
3. **为失败设计路径。** 仓库同步失败、Token 过期、重复提交等异常都有明确处理和提示。
4. **测试与文档同步推进。** 每周保留测试结果和截图，最终报告可以直接复用，而不是临时补写。
5. **如实记录约束。** 没有服务器就不把本地验证写成线上部署，交付文档与实际情况保持一致。

系统当前达到 v1.0 功能冻结状态，可作为课程答辩版本。后续如用于真实教学场景，需在数据库、文件存储、通知与部署方面继续完善。
